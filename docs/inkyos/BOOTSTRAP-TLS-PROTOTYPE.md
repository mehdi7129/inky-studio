# Bootstrap TLS — isolated prototype

This implements only the cryptographic primitives of the
[selected bootstrap design](BOOTSTRAP-TLS-DECISION.md). Nothing advertises a new
GATT service, selects bootstrap automatically, changes a clock, claims a frame,
modifies Wi-Fi, or enables InkyOS first boot. The deployed candidate is unchanged.

## Implemented boundaries

| Component | Behavior |
| --- | --- |
| `BootstrapFrameTrust` in the iOS app | Prevalidates a single DER and physically established identity using the existing P-256/SPKI/self-signature/name checks; evaluates Security's policy at an interior certificate date; exposes no HTTPS credential or normal trust policy |
| `BootstrapTLSConfiguration` / `TLSClient(bootstrapConfiguration:)` | Separate client construction; no generic date-ignore switch or fallback in normal construction |
| `inky_tls_create_bootstrap` | TLS 1.3, exact pinned leaf, P-256 and explicit ECDSA-SHA256 self-signature; required canonical CN/SAN, CA/key usage/serverAuth extensions; only the exact leaf's `EXPIRED`/`FUTURE` flags may be removed |
| Client handshake completion | Requires valid TLS transcript, exact `inky-bootstrap/1` ALPN and a single peer leaf before exposing plaintext; no tickets or early data |
| `BootstrapTLSContext` / `BootstrapTLSPeer` | Distinct server context and MemoryBIO peer; checks the negotiated ALPN after Finished and before any plaintext or handler task; reuses the existing bounded transport parser |
| Normal v1 client/server and HTTPS | Existing construction and certificate-date policy remain; shared Swift trust explicitly requires the generated leaf's digital-signature KeyUsage; no mandatory ALPN is retrofitted into v1 |

Python's server ALPN API can negotiate no protocol when offers do not match.
The explicit post-handshake check therefore remains mandatory. SNI filtering
is not implemented on the server; the pinned client verifies the expected name.
The bootstrap client rejects the normal server's absent ALPN, and the bootstrap
server rejects the normal client's absent ALPN before dispatch.

The certificate shape is intentionally restricted to the frame's generated
self-signed P-256 leaf, including its existing CA/keyCertSign properties. It is
not a general-purpose certificate-validation library. A renewed same-key leaf
must be supplied as the new exact anchor, after pin validation; an old DER anchor
cannot be used by clearing an untrusted-certificate error.

Two negative fixtures found and closed gaps during review: the C profile now
requires a strictly increasing validity interval before clearing date flags;
shared Swift trust explicitly checks the digitalSignature bit rather than
assuming Security checks that usage on a self-signed CA anchor. Certificates
generated by the existing frame identity already satisfy both requirements.

## Validation and reproducibility

All data used by these tests is synthetic. Generated test private keys stay in
ignored fixture directories. No real frame token, Wi-Fi credential, radio, clock
setting or Raspberry is used.

- `server/tests/test_bootstrap_tls.py`: real OpenSSL MemoryBIO handshakes, absent
  and wrong ALPN, TLS 1.2 rejection, altered Finished and application records,
  partial/bounded input, and Finished plus a pipelined command rejected before
  dispatch. Normal v1 transport tests run alongside this suite.
- `ios/Packages/InkyTLS/Tests/InkyTLSTests/`: actual Mbed TLS / Python OpenSSL
  interoperation over pipes, with synthetic certificate and record failures.
- `BootstrapFrameTrustTests` and `PinnedFrameTrustTests`: bootstrap prevalidation
  versus normal date-valid trust, malformed DER, identity/signature/usage failures
  and same-key renewal. These are distinct from proof of a TLS handshake.
- The pinned Mbed TLS 4.1.1 archive is checksum verified and rebuilt for device,
  simulator and macOS slices by `scripts/build-mbedtls-apple.sh`.

From a checkout with Python development dependencies installed:

```sh
python -m pytest server/tests
python -m ruff check server
scripts/build-mbedtls-apple.sh
INKY_TLS_TEST_PYTHON=/absolute/path/to/python bash ios/Packages/InkyTLS/Tests/InkyTLSTests/Support/generate-fixtures.sh
INKY_TLS_TEST_PYTHON=/absolute/path/to/python swift test --package-path ios/Packages/InkyTLS
```

The chosen Python must have `cryptography` installed. App tests use the checked-in
Xcode project with an iOS 18 or newer Simulator. The exact counts and build results
belong to the PR/checkpoint for the tested revision, not to a claim that these
commands have run on every platform.

## Integration still required

The raw TLS primitive accepts a supplied handler; it does not authenticate a
phone. It must not be registered as a service before a separate bootstrap-only
dispatcher enforces the QR/owner/epoch authority, schemas and operation allowlist.
Raw TLS success alone never authorizes a clock or factory mutation.

Still open: versioned GATT capability and command schemas, distinct app channel,
Keychain pending-claim flow, durable identity initialization before valid wall
time, root OS receipt adapter, serialized/fresh owner-authorized clock repair,
certificate renewal and strict reconnect, country gate, scheduler reconciliation,
and recovery after each persistence boundary. Factory orchestration must invoke
the root adapter's `begin` operation rather than replay a consumed grant file.

Physical iPhone QR/BLE, Wi-Fi commit/rollback, e-ink refresh and power-loss tests
remain required. This prototype closes none of the existing release candidate's
physical qualification gates and is not part of a stable-release declaration.
